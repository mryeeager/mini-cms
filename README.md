# Mini-CMS — وبلاگ شخصی روی Cloudflare (رایگان، بدون نیاز به کارت بانکی)

یک CMS شخصی سبک، شبیه نسخه‌ی کوچک وردپرس، که کاملاً روی سرویس‌های رایگان
Cloudflare اجرا می‌شه: **Workers** (میزبانی سایت، از طریق آداپتور رسمی
OpenNext)، **D1** (دیتابیس SQL)، و **Workers KV** (ذخیره‌ی فایل — به‌جای
R2، چون R2 نیاز به کارت بانکی داره).

## ⚠️ نکته‌ی مهم درباره‌ی D1 و KV قبل از هر چیز

`database_id` (برای D1) و `id` (برای KV) شناسه‌ی یک منبع واقعیه که باید
جایی توی اکانت کلادفلرت واقعاً وجود داشته باشه — هیچ مقدار عمومی یا
پیش‌فرضی نیست که برای همه کار کنه. به همین دلیل `wrangler.jsonc` این
پروژه دیگه هیچ مقدار placeholder (مثل `REPLACE_AFTER_...`) نداره؛ این
فیلدها عمداً خالی گذاشته شدن. سه راه برای پر کردنشون داری (پایین‌تر
توضیح داده شده) — هرکدوم رو انتخاب کنی، خطای قدیمی
`KV namespace ... is not valid (code 10042)` دیگه اتفاق نمی‌افته چون
دیگه هیچ رشته‌ی نامعتبری توی فایل نیست.

## 🚀 روش ۱ (پیشنهادی): اسکریپت خودکار — یک‌بار لوکال، بعدش گیت‌هاب

سریع‌ترین و مطمئن‌ترین راهه، چون همون چیزیه که این پروژه باهاش تست شده.
فقط یک‌بار لازمه، بعدش می‌تونی به گیت‌هاب وصل کنی و دیگه دستی به
`wrangler.jsonc` دست نزنی.

```bash
export CLOUDFLARE_API_TOKEN="توکن_خودت"
node scripts/setup.mjs
```

این اسکریپت خودش D1 و KV رو با CLI واقعی می‌سازه، `database_id`/`id`
واقعی رو توی `wrangler.jsonc` می‌نویسه، Migration ها رو اجرا می‌کنه،
دیپلوی می‌کنه، رمز امنیتی رو ثبت می‌کنه، و اکانت ادمین می‌سازه (جزئیات
کامل مراحل در بخش «روش ۲» پایین‌تر). جزئیات این توکن (چه مجوزهایی لازمه)
در بخش «توکن Cloudflare» پایین‌تره.

**اگه یه جایی fail شد** (مثلاً توکن اشتباه بود یا اینترنت قطع شد): فقط
توکن رو درست کن و دوباره همین دستور رو بزن — چون وضعیت مراحل قبلی از
روی خود `wrangler.jsonc` (برای D1/KV) و یک فایل وضعیت کوچیک
(`.setup-state.json`، فقط برای رمز امنیتی) تشخیص داده می‌شه، فقط از
همون‌جایی که گیر کرده بود ادامه می‌ده — نه از صفر. سازگار با Arch،
Fedora، Ubuntu، Debian، و Termux — چون فقط از Node.js استاندارد
استفاده می‌کنه.

بعد از اتمام اسکریپت، `wrangler.jsonc` حالا مقدارهای واقعی داره —
اونو Commit و Push کن:

```bash
git add wrangler.jsonc
git commit -m "Add real D1/KV resource IDs"
git push
```

حالا برو **Workers & Pages → Create → Connect to Git** و ریپازیتوری رو
وصل کن (Build command: `npx opennextjs-cloudflare build`). از این به
بعد هر Push جدید خودش دیپلوی می‌شه — دیگه هیچ‌وقت لازم نیست دستی
`wrangler.jsonc` رو ویرایش کنی.

## 🖱️ روش ۲: دستی با CLI (اگه ترجیح می‌دی مرحله‌به‌مرحله خودت انجام بدی)

```bash
npm install
export CLOUDFLARE_API_TOKEN="توکن_خودت"
npx wrangler whoami                                   # تأیید توکن

npx wrangler d1 create mini-cms-db
# خروجی شامل یه بلوک database_id هست؛ اون UUID رو کپی کن

npx wrangler kv namespace create MEDIA_KV
# خروجی شامل یه id هست؛ اون رو هم کپی کن
```

حالا `wrangler.jsonc` رو باز کن و دو تا فیلد رو خودت اضافه کن (الان
عمداً خالی‌ان):

```jsonc
"d1_databases": [
  {
    "binding": "DB",
    "database_name": "mini-cms-db",
    "database_id": "همین‌جا آیدی واقعی رو بذار"
  }
],
"kv_namespaces": [
  {
    "binding": "MEDIA_KV",
    "id": "همین‌جا آیدی واقعی رو بذار"
  }
]
```

بعد Migration ها رو روی همون دیتابیس واقعی اجرا کن:

```bash
npm run db:migrate:remote

npx opennextjs-cloudflare build
npx opennextjs-cloudflare deploy                      # اینجا Worker ساخته/آپدیت می‌شه

npx wrangler secret put SESSION_SECRET                # بعد از deploy، نه قبلش

node scripts/create-admin.mjs                          # دستور خروجی رو اجرا کن
```

بعدش `wrangler.jsonc` رو Commit/Push کن و مثل روش ۱ به گیت‌هاب وصل کن.

## ☁️ روش ۳: مستقیم از داشبورد کلادفلر، بدون هیچ دستور لوکال (Auto-Provisioning)

اگه اصلاً نمی‌خوای `npm`/`wrangler` رو لوکال نصب کنی: چون `wrangler.jsonc`
الان `database_id`/`id` نداره (نه مقدار placeholder، بلکه کاملاً حذف
شدن)، خود Cloudflare یه ویژگی به اسم **Automatic Resource Provisioning**
داره که در این حالت روی اولین دیپلوی، خودش یه D1 و یه KV تازه (با نام
بر پایه‌ی اسم Workerت) می‌سازه — حتی وقتی دیپلوی از طریق اتصال گیت‌هاب
(Workers Builds) باشه.

1. کد رو مستقیم به گیت‌هاب آپلود کن (بدون تغییر `wrangler.jsonc`).
2. **Workers & Pages → Create → Connect to Git** → ریپازیتوری → Build
   command: `npx opennextjs-cloudflare build` → Save and Deploy.
3. بعد از اولین دیپلوی موفق، برو **Worker → Bindings** توی داشبورد و
   ببین چه D1/KV ای واقعاً ساخته شده (آیدی‌هاش فقط از داشبورد قابل
   دیدنه، نه توی گیت‌هاب — طبیعیه، چون هیچ‌جا commit نشدن).
4. **حتماً Migration ها رو روی همون دیتابیس تازه اجرا کن** — این مرحله
   خودکار نیست: `npx wrangler d1 list` بزن تا آیدی واقعی رو پیدا کنی،
   بعد `npx wrangler d1 execute <اسم-دیتابیس> --remote --file=./migrations/0001_init.sql`
   و همین برای `0002_login_attempts.sql`. بدون این مرحله ورود به پنل
   مدیریت و ثبت نظر/پیام کار نمی‌کنه (جدول‌ها وجود ندارن).
5. رمز امنیتی و اکانت ادمین رو مثل روش ۲ (مراحل آخر) تنظیم کن.

> این ویژگی کلادفلر هنوز Beta‌ست و بعضی دستورهای فرعی `wrangler d1`
> (مثل migrations) هنوز باهاش صد در صد هماهنگ نیستن — برای یک بار
> راه‌اندازی مشکلی نداره، ولی روش ۱ برای این پروژه بیشتر تست شده و
> قابل‌اعتمادتره.

## امکانات هر بخش (خلاصه)

**احراز هویت ادمین** — بدون ثبت‌نام؛ Session سمت سرور در D1؛ قفل ۱۵ دقیقه‌ای
بعد از ۵ تلاش ناموفق؛ رمزها با PBKDF2 + salt هش می‌شن.

**مقالات و فایل‌ها** — ادیتور Markdown با پیش‌نویس/زمان‌بندی/انتشار؛ محتوا با
`marked` رندر و با `sanitize-html` پاک‌سازی می‌شه (ضد XSS)؛ فایل‌ها در
Workers KV ذخیره و از طریق `/api/media/<key>` سرو می‌شن؛ مصرف فضا از جدول
`media` در D1 محاسبه و با هشدار قرمز بالای ۸۰٪ نشون داده می‌شه؛ حذف فایل
همیشه با تأیید دستی ادمینه.

**بخش عمومی سایت** — صفحه اصلی، آرشیو، دسته‌بندی، برچسب، جستجو، درباره من،
تماس با من؛ RSS در `/rss.xml`؛ Sitemap و robots.txt خودکار؛ حالت تاریک/روشن.

**نظرات، ریپلای، ری‌اکشن** — نظرها بدون ثبت‌نام ثبت می‌شن، همه اول `pending`
می‌مونن و فقط با تأیید ادمین نمایش داده می‌شن؛ ادمین می‌تونه مستقیم ریپلای
بده؛ ری‌اکشن (👍❤️👏😄) روی مقاله و نظر، با فینگرپرینت هش‌شده ضد رأی تکراری.

**پنل مدیریت کامل** — داشبورد با آمار زنده (تعداد مقاله، بازدید، نظرات در
انتظار، پیام نخوانده، فضای KV)؛ مدیریت دسته‌بندی/برچسب؛ تنظیمات سایت (بدون
نیاز به تغییر کد)؛ تغییر رمز مدیر؛ صندوق پیام‌ها.

**PWA** — قابل نصب روی موبایل؛ Service Worker با کش هوشمند؛ صفحه‌ی آفلاین؛
دکمه‌ی نصب سفارشی برای Android/Chrome؛ پشتیبانی iOS با apple-touch-icon.

> ⚠️ آیکون فعلی یک SVG نمونه‌ست (`public/icon.svg`). قبل از انتشار نهایی،
> لوگوی واقعی بساز و با ابزاری مثل realfavicongenerator.net چند PNG
> (۱۹۲×۱۹۲ و ۵۱۲×۵۱۲) بساز و در `public/manifest.json` جایگزین کن.

## محدودیت‌های شناخته‌شده

- زمان‌بندی انتشار مقاله دقیق نیست (لحظه‌ی درخواست بعدی چک می‌شه، نه دقیقاً
  سر ساعت) — راه‌حل: افزودن یک Cron Trigger رایگان به `wrangler.jsonc`
- Workers KV سقف ۲۴ مگابایت برای هر فایل داره — برای ویدیو از یک پلتفرم
  بیرونی (آپارات) لینک بگیر
- آیکون PWA فعلاً SVG نمونه‌ست، نه ست کامل PNG
- بدون تست خودکار (unit/e2e) — برای پروژه شخصی در این مقیاس معمولاً لازم نیست

## گزارش تغییرات و بازبینی‌ها

### مهاجرت بزرگ: از Cloudflare Pages + next-on-pages به Cloudflare Workers + OpenNext

بعد از چندین خطای واقعی روی سیستم واقعی کاربر (ERESOLVE، نسخه‌ی نامعتبر
Next.js، ناسازگاری Wrangler 4)، مشخص شد که `@cloudflare/next-on-pages`
(پکیجی که این پروژه اولش باهاش ساخته شده بود) توسط خود Cloudflare
**Deprecated** شده و پشتیبانی از Next.js 14 رو هم قطع کرده. راه‌حل اصولی،
مهاجرت کامل به آداپتور رسمی و فعلی Cloudflare بود: **OpenNext**
(`@opennextjs/cloudflare`)، که روی **Cloudflare Workers** دیپلوی می‌شه
(نه Pages).

تغییرات این مهاجرت:

1. **`next`: نسخه ۱۴ → `^15.0.0`** — چون OpenNext دیگه از Next 14
   پشتیبانی نمی‌کنه. این یعنی `react`/`react-dom` هم به `^19.0.0` ارتقا
   پیدا کردن (Next 15 بهش نیاز داره).
2. **`params`/`searchParams`/`cookies()` حالا async هستن** — این یکی از
   تغییرات خود Next.js 15 هست (نه چیزی مخصوص Cloudflare). همه‌ی
   صفحات/مسیرهای دینامیک (`[id]`, `[slug]`, `[...key]`) و همه‌ی جاهایی که
   `searchParams` یا `cookies()` استفاده می‌کردن (`src/lib/session.ts`)
   به‌صورت کامل بازبینی و به `await params` / `await searchParams` /
   `await cookies()` تبدیل شدن.
3. **`@cloudflare/next-on-pages` حذف، `@opennextjs/cloudflare` اضافه شد.**
4. **`wrangler.toml` → `wrangler.jsonc`** — فرمت رسمی OpenNext؛ شامل
   `main`, `assets`, و همون بایندینگ‌های D1/KV قبلی. یک فایل جدید
   `open-next.config.ts` هم اضافه شد (فایل تنظیمات اجباری آداپتور).
5. **`src/lib/db.ts`** — دسترسی به بایندینگ‌ها از `getRequestContext()`
   (مخصوص next-on-pages) به `getCloudflareContext()` (مخصوص OpenNext)
   تغییر کرد.
6. **همه‌ی `export const runtime = "edge";` حذف شدن** — OpenNext روی
   Node.js runtime کار می‌کنه (نه فقط edge)، پس این محدودیت دیگه لازم
   نبود؛ حذفش هم ریسک ناسازگاری احتمالی رو کم می‌کنه.
7. **`wrangler`: نسخه ۳ → `^4.0.0`.** طبق راهنمای رسمی مهاجرت Wrangler
   v3→v4، دستورهای `d1 execute`/`d1 list`/`kv namespace list/create` که
   این پروژه استفاده می‌کنه بدون تغییر باقی می‌مونن (این دستورها همیشه
   عملیات سطح اکانت بودن، نه چیزی که تحت تأثیر پیش‌فرض local/remote
   Wrangler 4 قرار بگیره).
8. **دیپلوی از `wrangler pages deploy` به `opennextjs-cloudflare deploy`
   (که خودش `wrangler deploy` رو صدا می‌زنه) تغییر کرد.** رمز امنیتی هم
   از `wrangler pages secret put` به `wrangler secret put` تغییر کرد.
9. **مجوز توکن Cloudflare عوض شد** — `Cloudflare Pages Edit` دیگه لازم
   نیست، به‌جاش `Workers Scripts Edit` لازمه.

### بازطراحی کامل `scripts/setup.mjs`

طبق فیدبک دقیق کاربر بعد از تست واقعی، این اسکریپت از پایه بازنویسی شد:

- **ترتیب مراحل درست شد**: قبلاً رمز امنیتی قبل از دیپلوی ثبت می‌شد که
  باعث خطای «Project does not exist» می‌شد. حالا ترتیب دقیقاً اینه: نصب
  → بررسی توکن → D1 → Migration → KV → Build → Deploy → **بعدش** رمز
  امنیتی → ساخت ادمین.
- **بدون هیچ مقدار hardcoded** — اسم دیتابیس و KV از خود `wrangler.jsonc`
  خونده می‌شن، نه از رشته‌های ثابت داخل اسکریپت.
- **Resume واقعی** — هر مرحله قبل از اجرا چک می‌کنه که آیا قبلاً انجام
  شده (با خوندن `wrangler.jsonc` برای D1/KV، و یک فایل وضعیت کوچیک برای
  رمز امنیتی)، و فقط در صورت نیاز اون مرحله رو (دوباره) اجرا می‌کنه.
- **بدون نیاز به `--legacy-peer-deps`، `npm install-scripts approve`، یا
  `npm rebuild`** — چون بعد از یکپارچه‌سازی نسخه‌های next/react/wrangler
  با نسخه‌ای که OpenNext واقعاً پشتیبانی می‌کنه، دیگه تضاد peer dependency
  وجود نداره.

### بازبینی‌های قبلی (خلاصه)

پروژه چندین دور بازبینی عمیق شده — هم با خوندن دقیق کد، هم با اجرای واقعی
(کامپایل TypeScript واقعی، اجرای ۵۱ کوئری SQL روی SQLite واقعی، و در
نهایت اجرای واقعی روی سیستم کاربر که چندتا مشکل نصب رو آشکار کرد). برای
جزئیات کامل بازبینی‌های قبلی (jsdom/DOMPurify ناسازگار با Workers، حذف
دسته‌بندی fail می‌شد، و غیره)، تاریخچه‌ی گفتگو رو ببین — همه‌شون قبل از این
مهاجرت رفع شده بودن و توی این نسخه هم دست‌نخورده باقی موندن.

با این حال، چیزی که هنوز از سندباکس من قابل تست نیست: اجرای واقعی کامل
(`npm install` تا `deploy`) روی یک ماشین واقعی با اینترنت (سندباکس من
آفلاینه). این نسخه با دقت بیشتری بر پایه‌ی مستندات رسمی و فعلی Cloudflare
(نه فرض‌های من) بازسازی شده، ولی اگه به خطایی برخوردی، دقیقاً متن کامل
خطا رو برام بفرست.

### بازبینی چهارم — خطاهای واقعی از اجرای `next build` روی سیستم کاربر

روی سیستم واقعی کاربر، `next build` (که در Next 15 هم Type-check واقعی
انجام می‌ده) این خطا رو گرفت:

```
Type error: 'data' is of type 'unknown'.
setCategories(data.categories ?? []);
```

**علت:** توی نسخه‌های فعلی lib.dom.d.ts، متد `Response.json()` دیگه
`Promise<any>` برنمی‌گردونه — `Promise<unknown>` برمی‌گردونه (نوع
امن‌تر). یعنی هر جای پروژه که `await res.json()` رو مستقیم با یه property
(مثل `data.categories`) استفاده می‌کرد، خطا می‌داد. این کلاس خطا توی چک
ایزوله‌ی TypeScript من (که node_modules واقعی نداشت) قابل تشخیص نبود —
فقط خود `next build` با نوع‌های واقعی نصب‌شده می‌تونست پیداش کنه.

**اصلاح:** همه‌ی site‌هایی که `res.json()`/`req.json()` رو بدون اعتبارسنجی
zod مستقیم مصرف می‌کردن (۲۰+ مورد در کل پروژه — کامپوننت‌های پنل مدیریت،
و چندتا Route Handler سمت سرور) پیدا و با `as any` مشخص شدن. جاهایی که از
قبل با zod (`safeParse`) اعتبارسنجی می‌شدن دست‌نخورده موندن، چون
`safeParse` خودش ورودی `unknown` رو قبول می‌کنه.

در همین اصلاح، یه اشتباه کوچیک از خودم هم پیش اومد (یه find/replace
خودکار که `.catch()` رو اشتباه بعد از `as any` جابه‌جا کرده بود و باعث
خطای syntax می‌شد) — قبل از تحویل با یک بار دیگه اجرای کامل
type-check روی همه‌ی فایل‌ها پیدا و درست شد.

### روش جدید دیپلوی: گیت‌هاب + داشبورد (بدون نیاز به wrangler لوکال)

طبق درخواست کاربر، یک مسیر کاملاً جایگزین اضافه شد که هیچ‌وقت به
`npm install` یا دستورهای `wrangler` روی سیستم شخصی نیاز نداره: کد روی
گیت‌هاب آپلود می‌شه، D1/KV با کلیک از داشبورد کلادفلر ساخته می‌شن،
`wrangler.jsonc` مستقیم توی وب‌سایت گیت‌هاب ویرایش می‌شه، و **Cloudflare
Workers Builds** (اتصال Git) خودش build/deploy رو روی سرورهای کلادفلر
انجام می‌ده. تنها قدمی که همچنان به Node.js لوکال نیاز داره، ساخت
اکانت ادمینه (چون هش کردن امن رمز عبور باید لوکال انجام بشه) — ولی این
قدم به تنهایی هیچ `npm install`ی نمی‌خواد، چون `scripts/create-admin.mjs`
فقط از ماژول‌های داخلی Node استفاده می‌کنه.

### رفع خطای دیپلوی: `KV namespace ... is not valid (code: 10042)`

بعد از موفقیت‌آمیز شدن build، دیپلوی روی Cloudflare Workers با این خطا
fail می‌شد چون `wrangler.jsonc` هنوز مقدارهای placeholder
(`REPLACE_AFTER_WRANGLER_KV_CREATE` و `REPLACE_AFTER_WRANGLER_D1_CREATE`)
داشت — کلادفلر این رشته‌ها رو به‌عنوان UUID واقعی معتبر نمی‌دونه.

**اصلاح:**

1. **فیلدهای `database_id` و `id` کاملاً از `wrangler.jsonc` حذف شدن**
   (نه این‌که با یه مقدار دیگه جایگزین بشن) — چون هیچ مقدار عمومی‌ای
   نیست که برای هر اکانت درست باشه؛ این شناسه‌ها باید واقعاً وجود داشته
   باشن. حالا سه مسیر مستند شده که این فیلدها رو پر می‌کنن (بخش‌های
   «روش ۱/۲/۳» بالا)، از جمله ویژگی **Automatic Resource Provisioning**‌ی
   خود Cloudflare (وقتی این فیلدها خالی باشن، خود Cloudflare روی اولین
   دیپلوی یه D1/KV تازه می‌سازه — حتی از طریق اتصال گیت‌هاب).
2. **`scripts/setup.mjs` و `scripts/create-admin.mjs` برای پارس کردن
   کامنت‌های `//` توی `wrangler.jsonc` به‌روزرسانی شدن** — چون فایل
   `.jsonc` الان برای توضیح این تصمیم کامنت داره، ولی `JSON.parse` خام
   کامنت رو نمی‌فهمه؛ یه تابع کوچیک `stripJsonComments` قبل از پارس
   اضافه شد.
3. **متغیر `SITE_URL` کاملاً از `wrangler.jsonc` حذف شد** — چون خودش هم
   یه مقدار placeholder بود (`your-subdomain`). به‌جاش
   `src/lib/site-url.ts` اضافه شد که آدرس واقعی سایت رو مستقیم از
   Host header همون درخواست تشخیص می‌ده (`robots.ts`، `sitemap.ts`،
   `rss.xml/route.ts` همه ازش استفاده می‌کنن) — هم روی `*.workers.dev`
   درست کار می‌کنه، هم روی دامنه‌ی شخصی، بدون هیچ تنظیم دستی.
4. کل ریپازیتوری برای هر رشته‌ی `REPLACE_` یا placeholder دیگه‌ای grep
   شد تا هیچی باقی نمونده باشه.
